# 기능 명세

## 요약
자동차 경주 게임의 우승자 구하기

## 상세

1. 자동차 경주에 참가할 자동차 이름을 입력한다.
   - 입출력 예시
     - 출력: ``경주할 자동차 이름을 입력하세요.(이름은 쉼표(,) 기준으로 구분)``
     - 입력: ``pobi,woni,jun``
   - 시스템 제한 사항
     - 이름은 쉼표(,) 기준으로 구분한다.
     - 이름은 5자 이하만 가능하다.
2. 자동차 경주 동안 시도할 횟수를 입력한다.
   - 입출력 예시
     - 출력: ``시도할 횟수는 몇 회인가요?``
     - 입력: ``5``
3. 입력받은 시도 만큼, 자동차 전진을 누적해서 기록한다.
   - 입출력 예시
     - 출력:
          ```
          실행 결과
          pobi : -
          woni : 
          jun : -
          
          pobi : --
          woni : -
          jun : --
          ```
   - 시스템 동작
     - 0~9 무작위 값이 4 이상으로 나오면 전진한다.
     - 회차 별로 자동차의 누적 전진 수를 기록한다.
     - 마지막 회차까지 기록 후, 전진을 가장 많이 한 자동차가 우승한다.
5. 우승 자동차 이름을 출력한다.
   - 입출력 예시
     - 출력: ``최종 우승자 : pobi, jun``
   - 시스템 제한 사항
     - 공동 우승자가 있을 경우, 이름은 쉼표(,) 기준으로 구분한다.
   
### 입출력 제한 사항
- @woowacourse/mission-utils에서 제공하는 Random 및 Console API를 사용하여 구현해야 한다.
  - Random 값 추출은 Random.pickNumberInRange()를 활용한다.
  - 사용자의 값을 입력 및 출력하려면 Console.readLineAsync()와 Console.print()를 활용한다.

# 느낀점

### 요구사항 파악의 중요성

1주차, 그리고 이번 2주차 과제를 하며 요구사항을 정확하게 파악하는 것이 설계의 가장 큰 뿌리임을 체감했습니다!!
기능 명세를 직접 read me로 작성하는 과정이 번거롭게 느껴질 수도 있지만, 소프트웨어 공학 과목을 수강하며 "요구사항 분석은 아무도 안 해준다. 결국 개발자가 해야 한다."라고 하신 교수님의 말씀이 떠올랐습니다.
이번에는 조금 더 개선할 부분을 생각해보고, 다른 방식으로 작성해보았습니다.

use case description과 같은 문서에서 사용자와 시스템 동작을 분리하듯, 이번 명세에서도 따로 분리해보았습니다.
사용자 동작은 입출력밖에 없었고 따라서 입출력 예시를 따로 분류해서 작성했습니다.

각 기능이 어떤 책임을 가져야 할지, 그리고 어떤 부분에서 예외 처리가 필요할지 미리 예측하고 코드를 작성할 수 있었습니다.
특히 입출력과 검증 로직을 분리해서 생각할 수 있었습니다.
덕분에 단순히 기능을 나열하는 것을 넘어, 각 모듈의 역할을 명확히 나누는 설계를 고민하는 좋은 경험이었습니다.
